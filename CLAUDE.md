## Project overview

EBT (Brazilian steel-tube manufacturer) is replacing its legacy **Emissor NF** system (HDS / xHarbour / DBF files; old executable `D:\Projects\ebt project\EBT\SI\NF\NF.exe`) with **MetaGest**:

- Backend: ASP.NET Core 10 minimal API + EF Core + PostgreSQL 16 (`src/`).
- Clients: Flutter for Windows, Android and Web (`clients/flutter`).
- Modules: Engenharia (products, BOM, routing), Estoque, Suprimentos (purchasing), PCP (production), Vendas (sales), Fiscal (NF-e), Certificados (quality).
- UI language is Brazilian Portuguese. Code identifiers are English. Keep both.

### Backend conventions

- `EbtDbContext` is a **partial class**, one file per module: `EbtDbContext.cs` (engineering/master data), `.Inventory.cs`, `.Purchasing.cs`, `.Production.cs`, `.Sales.cs`, `.Fiscal.cs`, `.Certificates.cs`. Add a new module as a new partial file + entities file in `Entities/`.
- Endpoints: one static class per module in `src/Ebt.Api/Endpoints/` (`MasterDataEndpoints`, `ProductEndpoints`, `InventoryEndpoints`, `PurchasingEndpoints`, `ProductionEndpoints`, `SalesEndpoints`, `FiscalEndpoints`, `CertificateEndpoints`, `ReportsEndpoints`). Simple master data uses `MapCrud(new CrudSpec<TEntity, TIn, TOut>{...})` from `Infrastructure/Crud.cs`.
- Auth policies: `Policies.Read` etc.; roles include Admin, SalesManager.
- **Permissions** live in one matrix, `src/Ebt.Api/Infrastructure/Access.cs` (mirrored by `clients/flutter/test/role_permissions.dart` and described in `policyDescriptions` in `labels.dart`, shown on the read-only Permissões screen). Besides read/write/admin/stock: `sales-ship` = confirm the physical shipment (Admin, Sales, SalesManager, Stock); `fiscal-emit` = emit the sale NF (Admin, Sales, SalesManager); `fiscal-cancel`, `fiscal-prices`; `certificates` = draft certificates, `certificates-issue` = issue/cancel/delete a certificate and waive it on an order (Admin, Engineering, Production, SalesManager); `price-edit` = edit the price list (Admin, SalesManager). Adding a policy means touching all three places plus a test; `AccessParityTests` (backend) fails when `role_permissions.dart` or `policyDescriptions` drift from `Access.cs`.
- **Ship vs NF**: a caller without `fiscal-emit` (the Stock role) ships physically and, with fiscal enabled, the delivery is left without NF (history note "NF pendente"); Sales/SalesManager then emit it with `POST /api/sales/deliveries/{id}/emit-invoice` ("Emitir NF" button).
- **Source marker**: `DataSource` (Manual/Imported/Test, `Entities/DataSource.cs`, `IHasSource`) on Customer, Supplier, Product, Material, Quote, SalesOrder, Delivery, ProductionOrder, PurchaseRequisition, PurchaseOrder, StockDocument. DBF importers set Imported; the migration backfilled Imported from `legacy_code` (customers, suppliers) and `legacy_key` reports (OFs). Dashboard/report endpoints (`/sales/pipeline`, `/purchasing/overdue`, `/production/load`, `/reports/*`) skip Test unless `includeTest=true`; the dashboard lists pass `excludeTest=true`. Admin flags records with `POST /api/admin/data-source` (`entity`, `ids` or `allManual` (rows whose source is `from`, default Manual), `target`, `apply:false` previews; audited); `GET` returns counts per entity. Screen: Preferências > Administração > Manutenção de dados > Fonte dos dados (`settings_data_source.dart`).
- **Estoque mínimo**: `GET /api/stock/low-stock` (materials with `MinStock` above on-hand, minus open PO lines; suggestion up to `MaxStock`, rounded to `PurchaseLot`), `POST /api/stock/low-stock/requisitions` drafts one pending requisition per material (skips ones with an open requisition). Screen "Estoque mínimo" and a Painel alert. `MaxStock` is only used for the suggestion.
- **Duplicate detection** (`Ebt.Core/Duplicates/DuplicateService.cs`, `Endpoints/DuplicateEndpoints.cs`, entity `DuplicateDismissal` -> `duplicate_dismissals`): customers, suppliers and products only (materials have no record page), non-Test records only, nothing is merged. Customers/suppliers match on CNPJ/CPF digits (company + every address; 100), legacy code (95), name key without case/accents/punctuation/LTDA/S.A./ME/EPP (90), one name inside the other (75), similar names (70), same CNPJ root with another branch (60, hidden when the full CNPJ matches). Products: same code without separators (100), same measures (85), same name (70), same customer part number for the same customer (80). Score = best reason + 5 per extra reason, capped at 100; default minimum 60 (`?minScore=`). `GET /api/{customers|products|suppliers}/{id}/duplicates` (read policy) returns `{matches, dismissed}` for the record's own page (`DuplicatesBanner`, `widgets/duplicates.dart`, on the customer, product and supplier pages); `GET /api/duplicates/{kind}` returns groups (pairs joined transitively) for the screen Cadastros duplicados (`screens/duplicates.dart`, id `duplicates`), which is NOT listed in Preferências: it is reached from the "Atenção" strip (`DuplicatesAlert`, shown above the Clientes, Produtos and Fornecedores lists only when the server finds suspects; a tap opens the screen on that kind via `openDuplicates`). `POST/DELETE /api/duplicates/{kind}/{a}/{b}/dismiss` marks or un-marks a pair as "não é duplicado" (policy `duplicates-review`: Admin, Engineering, Purchasing, Sales, SalesManager; the row is audited, ids are plain numbers with no foreign key, the data reset never touches it). Matching is done in memory with key dictionaries, no n² pass over names beyond records that share a word.
- **Contas a receber** (`Ebt.Core/Receivables/ReceivablesService.cs`, `ReceivablesEndpoints.cs`, entity `ReceivablePayment` in `Entities/Fiscal.cs`): the duplicatas (`FiscalInstallment`) of Authorized sale NFs; payments (baixa, partial allowed, never above the balance, not in the future) are rows in `receivable_payments`, an estorno (`DELETE /api/receivables/payments/{id}?reason=`) flags the row reversed and keeps it. Nothing is stored on the installment: paid/balance/status (Open, Partial, Paid, Overdue against `Clock.Today()`, Cancelled when the NF is cancelled) are computed from the payments and the NF status, so a cancelled NF stops counting without touching `FiscalService`. Reading follows `read`; posting/reversing needs `receivables-post` (Admin, Sales, SalesManager). `ReceivablePayment` is audited. Data reset (Sales) clears the table first.
- **Usual IPI and ICMS per customer** (`Customer.IpiPercent`, `IcmsPercent`, `TaxNote`, in the `company` block of the customer, form "Editar cadastro"): a quote/order line takes them only when it has no typed rate and the price list gives none (`SalesService.BuildLinesAsync`); ICMS depends on the destination state, so the price list wins. They are learned from the old "Pedido Interno de Venda" workbooks: `scripts\export-customer-taxes.ps1` (reads the xlsx as zip, writes `customer-taxes.json`, git-ignored; `-Send` previews through the API, `-Apply` saves) -> `POST /api/customers/tax-import` (admin, audited, `apply:false` previews, `overwrite` replaces existing rates; `CustomerTaxImporter`). Customers are found by CNPJ (company or any address), then by 6-letter name key or trade-name prefix; ambiguous names are never guessed and come back in `unmatched`. The cadastro gets the rates of the latest order (dated, else year+sequence from the file name; years in the future are typos and skipped); `TaxNote` lists every rate seen with its state and count (IPI went 5% -> 3,25% over the years).
- **Printed-paper log**: `PrintLog` keys are per paper, not per screen: an OF is `of:<id>` whether printed from the order panel or from the OF screen, so "Impresso em" shows everywhere.
- **Credit limit**: `Customer.CreditLimit` overrides `PaymentTerm.CreditLimit` (`CreditCheck.LimitSource`). Exposure = unshipped value of open orders (`Open`) + open receivables of authorized NFs (`Receivable`) + the order being checked (`ThisOrder`); the three are returned by `GET /sales/quotes/{id}/credit` and named in the block message. Checked at order creation (existing), at release and at shipment (`SalesService.EnsureCreditAsync`): exceeded blocks with 409 unless the order already has a `credit-override` event or Admin/SalesManager sends `overrideCredit` (logged on the order history). The quote screen shows a warning banner, it never blocks approval.
- **Idle lock is server-side**: `PUT /api/auth/idle-lock {minutes}` stores the user's choice; `POST /api/auth/activity` only records `LastActivityAt` (a client value in its body is ignored); `TokenService.EffectiveIdle` applies the admin cap `Security:MaxIdleMinutes` (env `EBT_MAX_IDLE_MINUTES`, 0 = none; "never" and larger values become the cap) in token validation and refresh; `/me` and login return `idleLockMinutes` (effective) and `maxIdleMinutes`. The bootstrap admin may not use `sidergest123` outside Development/Testing, and passwords equal to it or to the username are rejected.
- **E-mail from the system** (`Ebt.Core/Mail`: `IMailSender`, `SmtpMailSender` on MailKit, config section `Mail`, env `EBT_SMTP_*` in `.env`/`compose.yaml`; off when host or from is empty): `GET /api/system/mail` -> `{enabled, from}`; `POST /api/sales/quotes/{id}/email` (`to`, `cc`, `subject`, `body`, `pdfBase64` built by the app, `fileName`) mails the PDF and, for a draft without pending approval or an approved quote, also registers the send (history `sent`); a Sent quote is mailed again (history `emailed`). Encryption by port (`EBT_SMTP_SECURITY`, Auto: 465 = SSL, else STARTTLS). Tests replace `IMailSender` with a fake. Setup in `docs/OPERATIONS.md`.
- **Health and alerts** (`Endpoints/OpsHealth.cs`, `AlertService.cs`): anonymous `GET /health/ready` returns `{status, db, pendingMigrations, backup:{lastOkAt, ageHours, agentSeenAt, drill}, warnings}`, 503 only when the DB is down or migrations are pending; warnings `backup_failed`, `backup_stale` (plan on, > 26 h), `agent_silent` (plan on, heartbeat > 10 min), `drill_failed` never make it 503. `AlertService` (hosted) checks the same every 5 min and mails `Alerts:To` (env `EBT_ALERT_TO`, off when empty or mail disabled) at most once per 6 h (last alert time in memory, no migration). compose also sets `Maximum Pool Size` (`EBT_DB_POOL`) and `mem_limit` (`EBT_API_MEM`, `EBT_DB_MEM`).
- **Price suggestion** (`Ebt.Core/Sales/PriceSuggestionService.cs`, `PriceHistoryImporter.cs`, `PriceSpec.cs`, `Endpoints/PriceSuggestionEndpoints.cs`, entity `PriceHistory` -> table `price_history`): `GET /api/sales/price-suggestion?diameter=&thickness=&length=&customerId=&quantity=&productId=&spec=` (policy `sales`; read-only roles get 403) returns weight (net, gross with the product loss or `TubeWeight.DefaultLossPercent` 2.8), a suggested R$/kg and per piece, the nearest past sales and the customer's last sale. Weighted 7-nearest-neighbours over the last 24 months of `price_history` plus live non-Test order lines (`Standard` gives their spec), distance `sqrt(4 ln(od)^2 + ln(wall)^2 + 0.1 ln(len)^2 + 0.6^2 if both specs known and different)`; a customer with a near repeat (distance < 0.25) gets its own last price (`CustomerRepeat`). `PriceSpec.Classify` maps spec text to STKM13A/GBK/NBK/BK/EN10305/NBR/SAE/other (checked in that order; the class names are also accepted as-is). `POST /api/sales/price-history/import` (CSV, policy `price-edit`, audited as PriceHistory/Import, upsert on `import_key` = first 6 letters of customer|dims|unit|price) and `GET /api/sales/price-history/summary`. Neighbours are also weighted by recency (`0.5^(ageMonths/6)`), `shape=rect` prices rectangular/square tubes like the oblong ones (same outside perimeter), and the response carries `repeat`, `suggestion.usedCount/newestDate/oldestDate`, `customerHistory`, `bySpec`, `trend`/`customerTrend` and an informational `customerFactor` (never applied: it made predictions worse). A history row that a live order line already covers is dropped; the loaded points are cached 60 s (`PriceDataCache`, config `PriceSuggestion:CacheSeconds`, cleared by an import). Saved simulations: `price_simulations` (`POST/GET/DELETE /api/sales/price-simulations`). History and simulations are reference data: `DataResetService` never touches them. It is built from the legacy workbooks by `scripts/export-price-history.ps1` (CSV git-ignored: real prices); see `docs/OPERATIONS.md`.
- **Old orders as history** (`CustomerTaxImporter`, `scripts/export-customer-taxes.ps1`, `POST /api/customers/tax-import`; flags `createMissing`, `apply`, `overwrite`): the same read of the order sheets also registers customers that are on orders but not in the cadastro (one per CNPJ, latest order wins, ambiguous names never created), completes empty contact/IE, corrects an IE only when 2+ orders of the customer carry it and no other customer does, adds delivery addresses named on the orders ("Endereço de entrega" note) and fills `order_materials` (customer + product code -> "BK DIN 2393", also the "bought before" history that makes the OF/PV say "Cliente cadastrado / Item já fornecido": `GET /api/sales/customers/{id}/novelty`). `GET /api/sales/material-suggestion` gives the steel standard for a paper whose line has none. Reference data; the data reset never touches it.
- **OF header**: `ProductionOrder.RawMaterial` ("Fita 1,20 x 42,50mm") and `PrimaryTube` ("Rolo 14,00 x 1,20 mm") come from the previous OF of the customer or the legacy template (`process_templates.raw_material/primary_tube`, exported by `scripts/export-process-templates.ps1`); `POST /api/production/orders/bulk/fill-materials` fills the empty ones of Created OFs. The OF PDF flows to a second page when needed (`_formsFlow`), so S.E.N.F and Inspeção Final are never cut off. A customer block prints the main (company) address; the delivery address chosen on the order goes in FRETE. A customer without a delivery address gets its main address copied (`POST /api/customers/{id}/addresses/from-main`). "Faturar para" prints under the prazo, only the chosen company.
- **Band saw / "Cortar as pontas"**: `OperationKind.Saw` (words SERRA or PONTA in the description or the resource, checked before the generic CORT of straightening) maps to the machine whose name has SERRA ("SERRA DE FITA", code SF001, added as data). The legacy sheets type some operation rows one cell to the right (description in column F, not E); `export-process-templates.ps1` reads F when E is empty and the row has a resource in M, and normalises "Cortas as pontas" to "Cortar as pontas". Roal 8 x 1 x 3000 had it on 45 sheets and lost it before that fix; re-export and re-import the templates after changing the script.
- **Legacy sheet layouts** (`export-process-templates.ps1`): newer workbooks have the ordem de fabricação on sheet 1 and the pedido on sheet 2 (the script finds the OP sheet by "PROCESSOS SECUNDARIOS"); numeric tolerance cells come out as "-0,5"; about 420 old sheets (2018-2022, and a layout with the description in column C) still give no operations (`-SkipLog <file>` lists them). Rolls and strips are not always as thick as the finished wall (drawing can thicken it), so no wall is rewritten; when another customer's process is borrowed (`TemplateDims`) the templates whose roll matches the wall come first (`ProcessSuggester.RollMatchesWall`). `GET /api/sales/material-suggestion` also looks at the same customer's same tube in another length (code stem "060.075.") before other customers. The OF/PV print the customer PO in its own field "PEDIDO DO CLIENTE:" (`customerPo`); the OF notes no longer get "PV n item n · pedido cliente" (`cleanOrderNote` also hides it on old OFs).
- **Client code and product of an old sheet**: `Customer.ClientCode` is the "CÓD. CLIENTE" of the paper sheets (not the legacy-system `LegacyCode`); `CustomerTaxImporter.LearnClientCodes` takes the number (3 digits at most) that most sheets of the customer carry (60%+ when 2+ sheets; a code wanted by two customers stays with the one with more sheets), the PV/OF print `clientCode` then `legacyCode`, never the database id. `PUT /api/customers/{id}` keeps it when `clientCode` is null and clears it when empty. The sheets' code cell is unreliable (empty, "ITEM NOVO" or copied from the previous sheet), so `ProductCodeOf` finds the product by the DIMENSÕES written on the sheet first (`order_materials`, novelty, usual notes). The OF/PV freight box: CIF ticks "ENTREGA POR NOSSA CONTA"; FOB writes "indicada pelo cliente (FOB)" on TRANSPORTADORA; "Retirada pelo cliente" ticks "CLIENTE RETIRA" and drops the delivery place. The final inspection always prints "Visual/Dimensional" as its resource.
- **Routing of every tube**: `POST /api/production/orders/bulk/fill-routing` (admin, `apply:false` previews, audited as Product/FillRouting; `ProductionService.BulkFillRoutingAsync`) gives each circular product named TUBO/TUB0 with the three measures and no routing the secondary process of `ProcessSuggester` for the tube without customer: the most common legacy process of that tube (only "sane" ones, `IsSane`: one profiling, drawing passes going down to the diameter, cut at the length) else the rules with `stepDown` (14 -> 12 -> 10 -> 8 -> 6 passes of 2 mm; whole sizes as "08,00"). Outside treatments (Beneficiamento, Tratamento, Recozimento, Zincagem) are a customer's requirement and stay out of the routing. Run on 2026-11-11: 282 products, 309 of 314 now have a routing (not tubes: scrap, forklift part, two coils). The OF copies the routing and fills tolerance by operation type.
- **Usual observation and material on the papers**: `order_materials.note` holds the observation a customer always puts on a product ("ISENTO DE OLEO E GRAXA", "Tratamento termico 30 HRB"); product "*" is the customer-wide one (a note on 70%+ of 5+ orders), a product row needs the note on half of 2+ orders and wins. `CustomerTaxImporter.TechnicalNote` keeps only tube-related pieces of the sheets' "OBS." cells (no PO numbers, quantities or logistics). `GET /api/sales/material-suggestion` returns `{material, note}`; the PV and OF print the order's own observation, else the usual one (OF: "O.C <po> <note>"). `_preferUsual` (print_docs.dart) swaps a material written without condition ("SAE 1005/1008 - DIN 2393") for the usual one with it ("BK DIN 2393") when both name the same DIN/EN norm. The OF PDF is always ONE A4 page: `_formsFlow` shrinks the blocks (FittedBox scaleDown) instead of paging.
- **Account and system endpoints** (`Auth.cs`, `SystemEndpoints.cs`): `POST /api/auth/sessions` lists own devices (`RefreshToken.Device/UserAgent/Ip`, login sends optional `device`), `DELETE /api/auth/sessions/{id}`, `POST /api/auth/sessions/revoke-others`; `PUT /api/auth/profile` sets `displayName`/`email` (returned by `/me`); `POST /api/auth/activity` (idle-lock heartbeat: `AppUser.IdleLockMinutes`/`LastActivityAt`, enforced in `TokenService.ValidateAsync` and refresh; the client sends it from `Session.reportActivity`); `GET /api/system/about`; admin `GET /api/admin/backup-status` (reads `status.json` that `scripts/backup.ps1` writes to `backup-status/`, mounted read-only as `Backup:Directory`; the dumps are never mounted).
- **Backup plan** (`SystemEndpoints.cs`, `BackupSettings`, admin only): `GET/PUT /api/admin/backup-settings` (on/off, frequency Hourly/Every6Hours/Daily/Weekly, time, weekday, destination folder or share, keep count) and `POST /api/admin/backup-settings/run-now`. Schedule rules are mirrored in `Ebt.Core/Maintenance/BackupSchedule.cs` and the agent; change both. `backup.ps1` verifies every dump (pg_restore -l, SHA-256 across the container copy and the destination copy), rotates only scheduled/manual dumps by count and gets the destination from `METAGEST_BACKUP_COPYTO`. Details in `docs/OPERATIONS.md`.
- **Audit log** (`Ebt.Core/Data/Audit.cs`): the interceptor logs inserts/updates/deletes of the master-data types in `Audited` and, for `ProductionOrder` and `QualityCertificate`, only status changes (action `Status`, who and from/to). - Business logic lives in `Ebt.Core` services (`SalesService`, `ProductionService` (+`.ShopFloor.cs`), `PurchasingService`, `StockService`, `FiscalService`, `CertificateService`, `BomService`), not in endpoints.

## Sales flow

**Orçamento → Enviada ao cliente → Aprovada → Pedido de compra → Pedido de venda → Ordem de Produção → Certificado → Entrega**

(8-step pipeline shown in `sales_pipeline.dart` / `widgets/pipeline.dart`. "Proposta" was renamed "Orçamento"; "condição de pagamento" renamed **Prazo**.)

- Quote requires customer and Prazo before lines can be added. Quote can carry a **custom prazo** (stored on quote, copied to the sales order). Customer has a default prazo.
- Quote estimate includes ICMS on top of IPI. IPI and ICMS are not typed on the item card; they come from the price table. Lines have lead-time **working days** (Mon-Fri, national holidays) synced with the delivery date; the server uses the same math when a quote becomes an order.
- Quote items require the unit price and a lead time in working days; the lead time counts from the day the customer approves the quote (`DecidedAt`), not from the day it was sent or converted, and the quote screen and PDF say so. The sales order dates are computed from the approval date on conversion.
- When the customer's purchase order carries its own delivery date for an item, it is typed on the "Registrar pedido de compra" step (`deliveryDates` on `POST /quotes/{id}/purchase-order`, stored on the quote line, history action `delivery-dates`) and wins over our lead time even when it is later; items without a customer date keep our date (approval + working days).
- Admins can delete draft, cancelled, rejected and expired quotes; a quote that already has a sales order is never deleted.
- Quote **revisions** use letter suffixes (A, B, C...). A revision replaces the earlier version, which is shown as **Substituída** (not "Cancelada"); the API exposes `supersededById`/`supersededBy` for it.
- **Quote outcomes** are named after what the customer did, not after system actions. While Sent: *Cliente aprovou* (accept), *Cliente pediu alteração* (revise: new revision, old one superseded), *Cliente recusou* (decline: status Rejected, shown **Perdida**, with a lost reason), *Prorrogar validade* (`/extend`; an Expired quote goes back to Sent). After approval or a purchase order: *Cliente desistiu* (decline with `CustomerGaveUp`, history action `gave-up`). Before sending: *Voltar para rascunho* (`/reopen`, from PendingApproval/Approved) and *Cancelar* (only for a quote that never left the company). Do not add menu items that duplicate these outcomes.
- Sales order carries company (EBT/BST), customer PO ("pedido de compra") step, and custom prazo.
- Production order (OF, "Ordem de Produção") is generated from the sales order; shop-floor operations in `ProductionService.ShopFloor.cs`. Operations can be done outside ("remessa para industrialização").
- The OF paper must always carry the whole process (middle of the sheet, "PROCESSOS SECUNDÁRIOS"). The process is the product's routing copied onto the OF. About 70% of the live OFs (imported legacy, products without routing) have none, so a new OF for a product without routing gets a **suggested process** (`ProcessSuggester.SuggestAsync(product, primaryTube, customerName)`, top-level standard OFs only, never imports or subassemblies). Tried in order: `PreviousOrder` (the latest non-cancelled OF of the same product and customer that has a tolerance), `TemplateCustomer` (legacy process of the same customer key + diameter ±0.01/thickness ±0.001/length ±1 mm), `TemplateDims` (the most frequent legacy process of the same tube for any customer), `Rules` (Perfilar from the primary tube, Trefilar para Ø, Endireitar e Cortar L, Inspeção Final; tolerances Perfilar/Trefilar "± 0,10", Endireitar e Cortar "+30" from 2500 mm, "± 0,05" from 500, "± 0,50" below, Inspeção "-"). Why: in the legacy OFs the tolerance is decided per customer and tube (99-100% identical between consecutive OFs of the same customer+dimensions, 51-76% when guessing the global mode), so a tolerance is never invented outside these sources. Legacy templates are reference data (`process_templates` + `process_template_operations`, one per customer key (`PriceHistoryImporter.CustomerKey`) + dimensions, latest OF date wins; the data reset never touches them), built from the legacy workbooks by `scripts/export-process-templates.ps1` and loaded with `POST /api/production/process-templates/import` (admin, audited; `GET .../summary`). Machines are matched by NAME keywords (`MachineIndex`: PERFILAD, TREFIL, ENDIREIT+CORTE then ENDIREIT, INSPE, ESCOV, POLI), never by id or code; template operations use their `resource` text first; types without a keyword (Beneficiamento, Tratamento) get no machine. In the legacy Excel "Visual/Dimensional" is the RESOURCE of the inspection and its tolerance is "-" (the old code had them swapped). When the product routing is copied onto a new OF, only its empty tolerance and missing machine are filled by the rule of the operation type. `POST /api/production/orders/{id}/process/suggest` returns the suggestion (`source`, `sourceRef`, operations with machine) without saving; `ProcessLine` takes an optional `machineId` (null keeps the operation's machine). The admin tool `POST /api/production/orders/bulk/complete-requirements` (`apply:false` previews) fills only the empty tolerance/machine of Created standard OFs without reports and turns the legacy "Visual/Dimensional" tolerance into "-". Order operations expose `machineName` next to `machineCode`. Before release the planner rewrites it with **Editar processo** on the Operações tab (`PUT /api/production/orders/{id}/process`, `ProductionService.ReplaceProcessAsync`; renumbers 10, 20, 30... by position and keeps material links). Legacy OFs already without operations are filled in batch by the admin tool **Limpeza do legado** (Preferências > Administração > Manutenção de dados; `POST /api/production/orders/bulk/suggest-process` and `/bulk/cancel-stale`, both admin only, preview first with `apply:false`). The tool also cancels Created OFs overdue for N days (min 30) with no stock movement or report, so imported legacy stops drowning the Painel alerts. Certificate specification templates are editable without issuing a certificate (`PUT /api/sales/certificates/templates/{id}`, "Editar modelo"). Shipping a delivery offers to print or download its issued certificates once (`printGate`, key `delivery:{id}:certificates:...`).
- **Order changes after release**: *Alterar prazos ou pedido do cliente* (`POST /orders/{id}/reschedule`, reason required for date changes, open OFs follow the new date), *Encerrar saldo* (`/close-balance`, only after something shipped: lines shrink to the shipped quantity, planned deliveries cancel, order becomes Expedido/Entregue), cancel shows a preview (`GET /orders/{id}/cancel-preview`) and can also cancel running OFs (`cancelProduction`, technical cancel). Shipping is blocked unless every item of the delivery has an issued certificate (for that order line, or for its product when the certificate names no line; one linked to another delivery does not count) or the order has a waiver, unless `withoutCertificate` is sent (logged as "sem certificado"). A certificate can only be issued with a found value on every row (remove the rows that do not apply); a delivery with a Pending NF (unknown SEFAZ outcome) cannot be cancelled.
- Delivery ("Entrega") ships from stock; with fiscal enabled, shipping emits the NF.
- **Real shipping routine (NF first, certificate after)**: the NF is issued only when the truck is ready to load, with the product weighed after the OF came back (the weight differs a little from what was asked); then the quality certificate is issued and carries the NF number. So: (1) **weighed quantity at shipping**: `ShipInput.Lines` (`ShipLineInput(DeliveryLineId, Quantity)`) replaces the planned quantity of each delivery line (`SalesService.ApplyFinalQuantitiesAsync`): above what is left to deliver only within `ProductionSettings.OverrunTolerancePercent` of the order line, below it the balance stays open (Encerrar saldo); stock, packages, gross weight and the NF use the new quantity, history action `final-quantity`; the ship form (`deliveries.dart`) has one "Quantidade pesada" field per item. (2) **certificate rule per customer**: `Customer.RequireCertificateBeforeShip` (default false; "Exigir o certificado antes de expedir" in the customer form, `company.requireCertificate`, left alone when the client does not send it). Only when it is true is shipping items without an issued certificate refused (`DeliveryOut.CertificateFirst`; the old "Expedir sem certificado?" question stays for those customers); otherwise it ships and the delivery is "Certificado pendente" (`DeliveryOut/Summary.CertificatePending`, filter `GET /api/sales/deliveries?pendingCertificate=true`, chip and badge on the delivery list, Painel alert "Entregas com certificado pendente", history note "certificado pendente"). (3) **NF number on the certificate**: a certificate drafted for a delivery takes `Delivery.InvoiceNumber` (`CertificateService.CreateAsync`), drafts made before the NF get it when the NF is typed or emitted (`FillCertificateInvoiceAsync`), and issuing a draft with a blank number takes the delivery's. The final weight is not stored on the OF in the system (the paper OF keeps it).
- **Sale unit and PO file on the order**: every quote/order item carries a Kg | Pç selector beside the quantity (`FieldSpec.unitOf`, key `saleUnit`, sent as `spec.saleUnit` KG/PC; the product's own unit is the default). On a quote line the server stores it in `Unit`; converting the quote passes it on as the order line's `SaleUnit` (`SalesService.SaleUnitSpec`). An order typed without a quote holds the customer's purchase order file itself (`SalesOrder.RequestFile*`, bytes in `sales_order_request_files`, `POST/GET/DELETE /api/sales/orders/{id}/request-file`, policy `sales`): the new-order form has an "Anexar" button (uploaded right after the order is saved) and the order page a "Pedido de compra do cliente" section; the print panel and `printGate` use it. The order path hides Orçamento/Enviada/Aprovada for such orders, and the step in progress is amber (`Tone.warning`) in every `StagePath`.

## Fiscal / NF

- CFOPs used: **5101** (venda), **5901** (remessa para industrialização), **5124 / 5902** (industrialização por encomenda / retorno), **5920 / 5921** (embalagem). All seeded in `cfops`; only 5101 and 5901 have emission triggers. Sale accepts another CFOP via `ship.cfop`.
- Emission off by default (`PUT /api/fiscal/settings`, `enabled: true`, needs full emitter data). Next NF number starts at 2581 (`fiscal_settings.next_number`), advances only on authorized NF.
- **Two issuers (EBT and BST)** (`FiscalSettings.Company`, unique; migration `FiscalIssuers`): `fiscal_settings` has one row per issuing company, each with its own CNPJ/IE/address, `Series`, `NextNumber` (EBT 2581, BST 897), environment, cancel window and `Enabled`. Row 1 is EBT, row 2 BST (seeded, emission off). `FiscalDocument.IssuerId` and `FiscalInutilization.IssuerId` say which row numbered the NF; the unique index is `(issuer_id, series, number)`. **Which issuer an order uses is its "Faturar para" (`SalesOrder.BillTo`, Ebt/Bts) through `FiscalCompany.Of`**, not `SalesOrder.Company`: the order forms never set `Company` (always EBT; only certificates read it), while "Faturar para" is what people choose and what prints on the papers. Sale: `IssueSaleAsync` reads the issuer of `order.BillTo`; a return, cancellation and CC-e follow the issuer of the original NF; outside shipments use EBT unless `OutsideInvoiceOptions.Company` says otherwise; inutilização takes `company`. Number reservation locks the issuer row (`LockSettingsAsync(c, issuerId)`), so EBT and BST never wait for each other. "Is emission on" is per company: `FiscalService.EnabledAsync(company)` for a delivery/order, `AnyEnabledAsync` for lists, KPIs and the credit exposure (`SalesEndpoints.FiscalFlags` for the delivery lists). API: `GET /api/fiscal/settings/all` (both rows), `GET|PUT /api/fiscal/settings?company=EBT|BST` (EBT when empty, 400 for another name), `GET /api/fiscal/legacy-import/summary?company=`, `POST /api/fiscal/inutilizations` with `company`; the preview and the document carry `company`/`issuerCompany`. **Legacy import**: the file's `source` (EBT/BST) picks the issuer it fills; for a BST file the tax rules and monthly prices cannot use `customers.legacy_code` (that is the EBT numbering), so the export lists the customers it refers to with their CNPJ/CPF (`customers` in the file, from NF010/NF020) and a code is mapped only when exactly one MetaGest customer has that document on an address (the section notes say how many matched; the rest is skipped). A non-EBT file only fills gaps: a rule or price that already exists with other values (the EBT data) is kept, never rewritten. Run on 2026-11-12: 37 of 98 BST customers exist in MetaGest. Tax rules, monthly prices, CFOPs and carriers are shared by both companies.
- Pricing: the sales order line price is the default; `monthly_prices` (product x customer x CFOP x month) overrides it, and a difference is kept as a warning (`fiscal_documents.warnings` + delivery history `nf-price-warning`). No monthly price: the order price is used; emission is blocked (422) only when neither exists. Taxes: `tax_rules` -> order item rates -> CFOP default CSTs.
- **"Emitir nota fiscal" step of the order** (`FiscalService.Preview.cs`, `GET /api/fiscal/preview/order/{id}`, `screens/order_invoice.dart`): step 6 of `flowSteps` (after Ordem de Fabricação, before Certificado; `orderPath`/`deliveryPath` indexes shifted by one, `invoiceStep`). The order page has an "Emitir nota fiscal" button (`order-invoice`) from the OF stage on; it opens a dry run of the whole order's sale NF (CFOP 5101, or 6101 for another UF; price, tax rule, ICMS/IPI/PIS/COFINS, duplicatas, transport, texts) plus a checklist of `NfProblem`s (issuer data, customer CNPJ/IE/IBGE/CEP, CFOP not registered, product without NCM, no price, no payment term; non-blocking: fiscal off, no A1 certificate, no tax rule, no net weight, each with where to fix). It also builds the NF-e XML and validates it against the XSD (problem "Layout da NF-e"). ICMS: tax rule, else the order line rate, else the state default in `icms_uf_rates` (legacy NF050, imported as `ufRates`). Nothing is reserved, saved or sent; the real emission still happens at shipment.
- **Fiscal data of the old system** (`Fiscal/FiscalDataImporter.cs`, `POST /api/fiscal/legacy-import?apply=`, admin; Fiscal > Importar do sistema antigo, `screens/fiscal_import.dart`, also still callable as the dialog `showFiscalImportDialog`): `scripts/export-fiscal-data.ps1` reads the legacy DBFs (NFCONTR issuer, NF270 carriers, NF050 ICMS per UF, NF090 tax regime per CFOP, NF070+NF020 CFOP per customer x product x address, NF100 monthly prices of the last 6 months) into `fiscal-data.json` (git-ignored, real prices). The legacy CFOP suffix (5101.00 with IPI CST 50 / 3.25%, .01 without IPI CST 55) is dropped from the code and carried by one `tax_rules` row per product x customer. The import previews first, fills only empty issuer fields, only raises the next NF number, never turns emission on, adds 6101, upserts carriers, tax rules and monthly prices (rows with unknown product/customer are counted and left out).
- **Pending: A1 `.pfx` certificate from the accountant.** Until then `StubSefazClient` runs (`simulated = true`; put `#SEFAZ-REJEITAR#` in observations to force rejection in tests). To enable real SEFAZ-SP set `Fiscal__Sefaz__Mode=Sp`, `Fiscal__Sefaz__CertificatePath`, `Fiscal__Sefaz__CertificatePassword` (env only, never in files) and start in Homologation.
- Done (all only against the stub, never SEFAZ): DANFE PDF (Flutter), XSD validation, inutilização, lookup by access key (reconcile, also scheduled every 10 min by `FiscalReconcileService`, `Fiscal:Reconcile:Enabled`), devolução (`POST /api/fiscal/documents/{id}/return`, CFOP 1202/2202, finNFe 4, stock back), CC-e (`POST .../correction`, event 110110), carrier registry (`/api/fiscal/carriers`) for the NF transport group, partial unique index on live NFs per delivery. Duplicidade 204/539 keeps the number and flags the NF (`KeyLookupRequired`) until reconciled. Not done: NF complementar, e-mail of the XML, devolução issued by the customer (entrada de terceiros), CC-e in the DANFE.

Two places plus the Fiscal module, by who the setting is for. Keep new settings in the matching place and do not add a fourth.

- **Preferências** (avatar menu; the menu itself only has Perfil and Preferências plus the quick theme/size controls; `settings/settings_dialog.dart`): personal sections (Aparência e impressão, Geral, Notificações, Conta e acesso, Dispositivo e sobre; related ones are merged, and the old ids `print`/`about` still open the merged section), then ONE heading, *Administração* (admins) or *Sistema* (everyone else), with **Parâmetros dos módulos** as a section of the window itself (`SettingsScreen(embedded: true)`: four short cards that fit; the page `id: settings` stays for links and the palette), then the system screens that need a page as links (they close the window and open on the main one through `SettingsLinks.open`, set by the Shell; the `open_in_new` icon says so): for admins **Usuários e acesso** (one entry, a `TabGroup` with the tabs Usuários, Permissões, Auditoria); they are the `NavItem`s of section `Sistema`, filtered by `shownTo`, minus `_notListedHere` (`duplicates`, `settings`)). The window is up to 1240x860 and its sections lay their groups in two columns when the content is 830 px or wider (`SettingsGrid`, one column below); a new section should build a `SettingsGrid` of `SettingsGroup`s and the admin sections **Backup** and **Manutenção de dados** (Fonte dos dados, Limpeza do legado, zona de perigo "Limpar dados de movimento"). No fiscal tool is here.
- **Fiscal module** (sidebar, `section: 'Fiscal'`, Ctrl+6): overview = readiness checklist (`screens/fiscal_readiness.dart`: per company (EBT, BST) "Dados do emitente" and "Emissão de NF-e" (on/off, série, próximo número); shared: CFOPs 5101/6101, regras de imposto, transportadoras, certificado A1 (SEFAZ simulada = sem certificado); built from `/api/fiscal/settings/all`, `/cfops`, `/legacy-import/summary`; each pending line opens the screen that fixes it, the company going as the screen filter). Tab groups: *Notas e cobrança* (Notas fiscais, Contas a receber) and *Parâmetros fiscais* (Emitente e emissão = `fiscal-settings` with one tab per company (EBT/BST), Regras de imposto, Preços mensais da NF, Transportadoras = `carriers` spec on `/api/fiscal/carriers`, write policy `fiscal-emit`); plus *Importar do sistema antigo* (`fiscal-import`, admin). Screen ids and record kinds did not change, only their section, so links, pins, history and the address bar keep working.

Naming: "Parâmetros" always means system rules (Parâmetros dos módulos, Parâmetros fiscais); "Preferências" is only personal. Server messages that say where to fix something (`FiscalService.Preview.cs`, `FiscalDataImporter`, `AlertService`) use these names.
## Gotchas

- Do not edit generated migration `.Designer.cs`/snapshot by hand; regenerate via `dotnet ef`.
- PCP/navigation tests depend on sidebar height (see commit "Fix PCP nav tests for taller sidebar"); adding nav items can break `app_test.dart`.
- SEFAZ timeout means unknown outcome; check access key in portal before re-emitting.
- README.md has the user-facing quick start; this file is the engineering context.
- Many Flutter and docs files are CRLF in the working copy; `dart format -l 160` on a whole old file produces noisy diffs. Format only what you wrote.
- A stale app window shows old code: stop it and run `flutter run` again from `clients/flutter` on `main`. Release Android builds block cleartext HTTP; use HTTPS (debug builds allow it).
- PowerShell scripts that contain accented text (`backup.ps1`, `backup-agent.ps1`) are saved as UTF-8 with BOM: Windows PowerShell 5.1 reads BOM-less files as ANSI and double-encodes the accents. Keep the BOM when editing them.
